# DJQ 试玩反馈与下一版设计

日期：2026-10-16。本文保留开发前评估。用户随后回复“继续”，当前已实现并完成自动化验收；实际结果见开发计划执行记录、GAME_SPEC.md和VERIFICATION.json。实体触屏与生产域名验收另行进行。

## 目标与已确认需求

让桌面和手机都能自然地摆放棋子，减少开局步骤，使落点提示有选择价值，并支持机器人与四人组队。

用户明确要求：按住拖动改变位置；直接点击拼图旋转；拼图不能超出棋盘；取消准备；智能机器人；两人双色；四人双色组队；提示优先大棋子并支持旋转、翻转。

用户已确认四人组队含义：四人分两队，每人一色，每队合计双色，按队伍总分结算。以下细节是本计划建议的默认值：对角颜色同队；房主手动开始；保留独立确认落子；仅未落定的预览棋子可拖动、旋转。它们不是已完成的功能。

基线提交：`f8ecc99`。技术栈：Node.js >=22、原生 ES Modules、SVG、HTTP/SSE、node:test；零 npm 运行依赖。

本次执行 `npm test`：49/49 通过。阅读发现旧浏览器测试主要走“提示→确认”，手机手动落子只测 I1，不能证明多格棋子的拖放体验正确。上述交互根因来自代码检查，尚未在真实手机复现或修复。

## 方案选择

1. **建议：针对现有模块分阶段改进。** 新增交互、候选走法、策略、调度模块，保留现有规则权威与SSE；复用成本低，能先独立交付交互修复。
2. 只在 app.mjs 加事件补丁：交付快，但拖动、点击、触摸、机器人和联机重绘会继续互相影响，不适合这次范围。
3. 重写前端或接入外部大模型机器人：迁移面和运行成本增加，不能直接解决落点锚点问题，不纳入本轮。

## 1. 落子交互

- 桌面和手机使用同一 Pointer Events 状态机：`idle → pressed → dragging → preview`。按下后位移达到 **8 CSS px** 才算拖动；“按住”无需等待长按计时。
- 点击棋子托盘选择形状，立即在棋盘生成完整预览：已有预览时沿用其锚点；首次选择时，未开局颜色靠近起始角，已开局颜色靠近棋盘中心。初始锚点选形状中距几何中心最近的实心小格，同距按 y、x 排序。
- 从预览的任意实心小格抓取，保存棋盘坐标系中的指针偏移。鼠标/手指停在哪一格，抓取的部位就保持在该位置，不能跳到左上角。空洞与包围框空白不算命中。
- 鼠标悬停、点击预览以外的空棋盘不移动预览；位置修改必须经过拖动或方向键。托盘的鼠标拖入可保留，但走同一状态机；手机先点选、再在棋盘拖动，避免与托盘滚动冲突。
- 松开只固定预览位置，不自动提交；用户仍点击“确认落子”或 Enter。未达到拖动阈值的预览短按顺时针旋转90°；拖动松开不能再触发旋转。
- 旋转以被点击的实心小格为支点；工具栏/键盘旋转使用当前预览锚点。翻转按钮与 F 保留。变换后重新计算原点和尺寸，必要时整体平移回棋盘。
- 形状宽 w、高 h 时，原点必须满足 `0 ≤ x ≤ 20-w`、`0 ≤ y ≤ 20-h`。选形、移动、提示、旋转、翻转、键盘均走同一边界函数。不能用截掉预览小格的方式隐藏越界。
- 重叠、不连角、同色贴边仍可显示完整红色预览，确认禁用并解释原因；不主动把棋子跳到另一个合法位置。
- 按下时捕获 pointerId；拖动只响应同一指针，第二根手指不能接管。pointercancel、失焦、失去捕获回到拖动前的位置且不旋转；收到新回合/revision时清空旧交互；仅连接状态重绘不能破坏进行中的拖动。
- 预览命中使用逻辑格坐标，已落定棋子保持不可编辑。棋盘外可正常滚动；棋盘触摸按游戏手势处理，保留明确的页面滚动区域。

## 2. 合法走法与提示

- 新增惰性、穷尽的候选生成器：复用连接点、`variants` 与 `validateMove`，按绝对占用格去重。颜色无合法走法判定继续穷尽，不能因提示数量或机器人预算而误判堵死。
- `findMove(game, color, preferredPiece)` 保持现有签名与首个合法结果语义，内部取生成器第一个结果，维持旧测试和超时兜底。
- 默认提示面向全部剩余棋子，按格数降序：有5格合法走法时先推荐5格；之后4、3、2、1格。选中了小棋子也不限制默认提示范围。
- 同格数先每种可走棋子展示一个高评分走法，再轮换这些棋子的其他落点/姿态，避免反复只见一个棋形。同格数组内按后续连接点、扩张空间评分，再按稳定坐标打破平局。
- 全部独特候选构成有限循环；连续点击显示“方案 i/N”，走完循环后才允许重复。状态未变不能重复首个方案；确实只有一个候选时显示“仅此1个可行方案”。大块组轮完再进入小块组。
- 每条建议同时更新棋子、姿态、位置和托盘缩略图；可显示“5格／已旋转／已翻转”。建议不是自动落子，之后仍能拖动、旋转、翻转和确认。
- 缓存键包含游戏实例、round、revision、color；本地悔棋/导入/重开需失效，即使 revision 数字重复。搜索在worker执行，旧请求结果必须丢弃。

## 3. 模式、队伍与兼容

| mode | 人数 | 控制与胜负 |
| --- | --- | --- |
| `duo` | 2 | P1蓝+红，P2黄+绿，按个人双色总分 |
| `trio` | 3 | 保留公共绿轮换与不计分规则 |
| `classic` | 4 | 保留四人各自计分 |
| `teams` | 4 | P1蓝/P3红为A队，P2黄/P4绿为B队，按队伍双色总分 |

- 人数与模式分开校验，拒绝 teams+2人等不一致配置。所有模式仍是20×20、四色各21块，固定蓝→黄→红→绿；不引入八色。
- 队友仍只控制自己的颜色；同色连角/禁贴边规则不变，队友的另一种颜色视为异色，不能提供本色连接。队伍关系只影响策略和计分。
- 四人组队显示成员与颜色、个人贡献和队伍总分；结算以队伍为单位，同分可并列。奖励先按每色计算再合计。
- 组队中一人认输仅停止该人颜色，队友继续；任一队两人均认输时该队判负。自然结束时按总分比较；已认输颜色的剩余扣分仍计入队伍。其余模式保持原有认输规则。
- 旧 `newGame(players, scoring)` 调用仍有效，第三个可选参数传模式；旧二维控制与三人公共色不改语义。
- 棋谱输出升级v2，带mode与席位类型/机器人档位；仍通过执行动作验证。v1按人数映射旧模式，旧本地存档直接读取并在下次保存升级，不删除旧记录来规避兼容。
- 保留 `automatic`；v2可附加 `source: human | bot | timeout`，区分机器人和超时托管。恢复棋谱只重放历史，不重新运行机器人。恢复本地机器人对局需先完成校验和UI恢复，再调度当前回合。

## 4. 取消准备、开局与再来一局

- 移除按钮、成员ready字段与服务端ready前置条件；不采用“全员进房立即开局”。满员后由房主点“开始对局”，便于确认模式和席位。
- 开始条件：房主是有效在线真人；所有席位已占用；真人席位在线；机器人席位配置有效；房间处于waiting。机器人不依赖SSE连接，也不拥有token。
- 再来一局返回等待房间，保留尚在的真人与机器人配置，离开的真人席位置空；满足开始条件后房主再次开始。取消准备不等于移除房间状态、round和revision。
- 废弃ready命令返回明确错误，前后端同版发布。开始缺人/离线分别给出明确原因，不继续使用“等待准备”的文案。
- 等待房间中仅房主可以把空位设为机器人、移除机器人、修改其档位。不得替换已占用的真人，也不因断线自动把真人变成机器人；原断线与超时机制保留。
- 真人加入只找空位；全是机器人占位时提示房主先移除机器人。房主转移只选择有效真人；没有真人剩下则清理房间，不能把机器人升为房主。

## 5. 智能机器人

第一版先交付一个“标准”策略档位与本地/在线混合席位。更深搜索与多个难度等基准完成后再评估，避免将未验证棋力称为竞技AI。

- **目标：** 相比现有“首个合法走法”，考虑未来可用空间与连接能力，能独立完成2/3/4人和组队对局。
- **决策：** 枚举合法走法，优先候选中同时考虑放出格数、有效新增连接点、可达空间、向外扩张、对手通路、紧凑空隙填补和单格收尾奖励。大块是高权重而非绝对规则，残局可为更高总得分选择小块。
- **模式感知：** 两人把自己的双色视为同一收益主体；组队优化队伍收益，阻挡项只针对敌队，避免把队友扩张当敌方威胁；三人公共绿以当前控制人的后续利益评价，不把绿的得分计入个人。
- **执行：** 浏览器使用 Web Worker，服务端使用有界 `worker_threads` 池（建议初始2个worker）；公共策略代码不依赖 DOM、网络或全局可变局面。整份游戏快照输入，返回落子意图，权威线程再次校验后执行。
- **预算：** 默认每次候选评价400ms，执行硬超时1000ms；这是待测目标。首个合法走法作为兜底，worker失败/预算耗尽仍可落子。合法性/无棋可走判定不能受策略预算截断。
- **调度：** 每个局面最多一个机器人任务。结果携带游戏实例、round、revision、color、seat和配置代次；悔棋、重开、房主改配置、回合已变时拒绝旧结果。动画/思考展示与真实搜索分离，不靠客户端定时提交联机机器人棋步。
- **权限：** 联机机器人由服务端调度；真人提交机器人回合落子仍拒绝。机器人不参与认证token、会话恢复记录、连接数、房主候选；机器人活动不刷新lastHuman。所有真人离线时暂停机器人调度并沿用房间清理策略，已到真人截止时间的超时规则仍按现有约定执行。
- **悔棋：** 纯真人同屏仍退一手；含机器人的本地对局回到最近一次真人决策之前，连带撤销其后机器人行动，取消旧计算，避免刚悔棋就自动重下。
- **棋力验收：** 固定种子、轮换先后手，与现有 findMove 基线对弈；双人双色至少40局，目标胜率≥60%（平局计0.5），并比较平均放出格数。四人和组队另做轮换席位基准，报告分布，不用双人胜率代替。未达目标需调参和复测，不以“能自动下完”宣称智能验收通过。

## 6. 验收与发布边界

先交互与提示，后模式与开局，再机器人与回归。每阶段必须能独立游玩，不能等机器人完成才修复落子。

桌面验收覆盖非单格形状、正常鼠标、方向键、按钮/棋盘焦点；手机覆盖多格棋子任意小格抓取、点击旋转、四边拖拽、翻转、页面滚动、多指和取消手势。自动化使用真实HTTP来源的浏览器测试，另用实体安卓/iOS触屏做手感验收；没有设备时如实标为未验收。

所有旧49项测试按新规格更新与保留，增加交互、候选去重/姿态、组队、机器人调度、过期结果、worker失效、旧棋谱兼容测试。完整流程包含同屏/联机、恢复席位、重连、超时、再开、复盘、导出、构建产物静态模块可达性。

继续使用当前单进程房间与零运行依赖。无需更换前端框架、数据库或部署方式；本轮不新增账号、排位、聊天、观战、全量架构重写。开发计划不包含自动部署授权。
